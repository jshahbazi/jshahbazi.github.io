Setup: I maintain a small Django site for a nonprofit that tracks policy actions. It runs on Elastic Beanstalk behind CloudFront and an AWS WAF, with a single Postgres instance on RDS. Normal traffic is about 9,500 requests an hour, mostly crawlers hitting the policy search page. Early on the morning of September 29 I got a message that the site was down. A botnet had started sending about 19 times the normal traffic overnight, all of it to the search page, and the load balancer was returning 503 to everyone. This is a writeup of the 25 minutes between the first command and the block, what Claude and I each got right and wrong during that time, and the seven pull requests that followed. All times are Eastern.

<!--more-->

## What the site looked like from the inside

The one thing that matters about the architecture of the site is that search was the most expensive page on the site and nothing stood between it and the database.

- CloudFront's default behavior had caching disabled, so every request reached Django.
- The WAF had a per-IP rate limit (100 requests per 5 minutes) and AWS Bot Control at the level that only recognises bots that identify themselves, with every category set to count rather than block. No rule looked at the Referer header.
- The search view computed a Postgres full-text vector over every live policy on every request, with no stored vector and no index, and evaluated that queryset about 4 to 5 times per page. A context processor also wrote a search-hit row to the database on every request carrying `query=`.
- Each instance ran 7 gunicorn workers with 4 threads each. The health check endpoint doesn't touch the database, but it queues behind requests that do. When all 28 threads were waiting on Postgres, the health check hit the load balancer's 10-second timeout, the load balancer marked the instance out of service, and it answered 503 to everyone.

So one slow page, under enough load, took the whole site down with it. Adding instances only added database connections. The autoscaler did exactly that at 8:06 PM and it made no difference.

## The botnet

| Figure | Value |
|---|---|
| Requests seen at CloudFront, 7:00 PM Sept 28 to 9:59 AM Sept 29 | 1,399,690 |
| Of which above the ~9,500/hour baseline | about 1.26 million |
| Peak hour (8:00 AM) | 181,710, about 19x normal |
| Requests that reached nginx | about 345K |
| 5xx responses generated by the load balancer | about 1.07 million |
| Source IPs | at least 210,000, about 1.6 requests each |
| Busiest single IP | 25 requests in 17 hours |
| Countries | 101, none above 8% |
| User-agent strings | 8, rotated in near-equal shares |
| Requests to `/policies/?…` | 99.97% |

The IPs are residential proxies: consumer devices whose connections are resold, spread across 101 countries. A per-IP rate limit does nothing against 210,000 addresses sending 1.6 requests each. The user agents were Chrome and Edge versions 6 to 10 months old, with complete, browser-like headers. Bot Control saw nothing wrong.

The motive was search-results SEO spam. The search page echoed the `query` parameter into the page heading, so any URL of the form `/policies/?query=<text>` was a page on a reputable `.org` domain displaying the spammer's text. 99.4% of the payloads advertised one domain, which the spam presented as a stolen-card shop. This wasn't new: in the week before the attack, 90% of `query=` requests came from declared crawlers and 71% carried spam text. The botnet was the same mechanism at a volume the database couldn't take. Until one of the follow-up PRs, the echo wasn't escaped either, so the same line was a reflected XSS.

Within five minutes of the botnet's arrival at 7:31 PM on September 28, RDS CPU went from 20-36% to 98.8% and stayed at about 99% until 8:38 the next morning. Connections went from about 20 to 105. Load balancer 5xx went from 41 to 2,545 per five minutes.

## The 25 minutes

I started with Claude at about 8:05 AM, giving it access to the AWS CLI and the production logs and asking it to find out why Elastic Beanstalk was reporting "59.1 % of the requests to the ELB are failing with HTTP 5xx". I read the output and approved anything that changed state. Here is what happened, including the parts that didn't work.

| Time | What happened |
|---|---|
| ~8:05 AM | First commands run against us-east-1, the CLI default. Everything except the WAF is in us-east-2. A few minutes lost before the region was corrected. |
| 8:11-8:13 AM | My first hypothesis: Spot instance churn. Instances had been reclaimed daily, which was real but chronic, and it was the thing I already knew was wrong with the environment. I had two instances terminated and one rebooted. The database went idle within a minute (connections 61 → 0, CPU 99% → 2%), the replacements passed health checks, and by 8:17 the database was back at 104 connections and 99% CPU. |
| 8:13-8:20 AM | Claude found the clue that ruled out Spot churn: load balancer traffic was at 6x normal while backend 2xx responses stayed flat. The backend was saturated, not broken. |
| ~8:20 AM | Second hypothesis: crawlers. The first nginx sample showed bingbot and Applebot on spam search URLs. Counting requests by user agent found 8 generic browser strings with about 43K requests each. Bingbot had been heavier the day before, when the site was fine. |
| ~8:25 AM | Claude briefly reported the Referer as missing on 99.9% of requests. It was present, with one unusual value, on 99.9% of requests. The column had been misread. |
| 8:25-8:29 AM | The signature was checked against a week of logs before blocking (see below). Claude drafted the WAF rule as a full `update-web-acl` input, ran `check-capacity`, and showed me the diff. |
| 8:30:00 AM | Rule applied. Verified at 8:30:27 with curl: the forged header gets a 403; the same header with a trailing slash, or no header, passes. |
| 8:30-8:39 AM | WAF blocking 2,100-3,000 requests a minute. Traffic reaching nginx falls from 1,000-1,900 a minute to 10-120. CloudFront 5xx rate is 0% from 8:35. Load balancer 5xx reaches zero at 8:39. |
| 8:38-8:43 AM | Database drains, 99% → 12%. Homepage returns 200 in 20 seconds at 8:38. |
| 8:46:11 AM | Elastic Beanstalk health back to Ok. Search page loads in about 3 seconds. |
| 9:24 AM | The botnet stops, about 55 minutes after being blocked. It had not returned with a new fingerprint as of 10:38 AM. |

## The signature

The botnet set the Referer header to the site's own origin, with no trailing slash. Browsers serialize an origin-only referrer with the trailing slash, so this value can't come from a browser; the string was built by hand in the bot's code. It was on 99.9% of the botnet's requests.

The step that made a same-hour block safe was counting first. Claude pulled a week of WAF logs and counted requests carrying that exact value on quiet days: 12 to 33 a day, mostly scanner junk. During the attack it was 2,000 to 3,500 a minute. There was no legitimate traffic to lose.

The rule itself is small: a byte match on the `referer` header, exact match, no text transformation, action Block, at priority 0 with the existing rules shifted down. It moved the ACL from 1,178 to 1,180 capacity units, costs about $1 a month, and because it runs first, blocked requests skip Bot Control's per-request fee.

Claude also found a second tell: `sec-fetch-site: none` together with a Referer, on every sampled botnet request. Browsers send `none` for user-initiated navigations, which normally carry no Referer. But on the quiet day of September 27, 1,269 requests from current-looking browsers had the same combination, so it isn't clean enough to block on alone. It's written down as a backup and not deployed.

## What went wrong

These are method notes rather than complaints. Every one of them was caught within minutes, and each one is a rule I'd now put in the instructions file before the next incident.

- Restarting instances (me). I went straight to the problem I already knew about. Terminating and rebooting cost capacity and changed nothing, because the instances were never the problem. Rule: when every instance is unhealthy at once, suspect the shared dependency before the instances.
- A misread column (Claude). The Referer was reported missing when it was present with a forged value. Rule: when a column reads as 99.9% anything, look at the raw rows.
- An unused log source (both of us). The 30-day WAF log group in us-east-1 had every header of every request. The investigation worked mostly from nginx logs, which saw about a quarter of the flood, and WAF sampled requests, which go back 3 hours. Rule: list the log sources and their retention before you start reading any of them.

Claude's mistakes were mechanical (a default region, a column, a timestamp format) and were caught by me reading its output. My mistake was the human one: pattern-matching to the last problem I'd seen. Claude caught that one by showing me a number that didn't fit. Either of us alone would have been slower; the agent's speed made the wrong turns cheap, and the Spot detour cost about seven minutes.

## The fixes

Blocking one header stops one botnet. The site was a target because search was expensive, and the September 24-26 wave (200,049 requests from 108,388 IPs on the 24th alone, with 65,506, 64,737 and 36,061 load balancer 5xx on those three days, and about 13 hours of RDS at 92-99%) had no Referer at all and would have passed straight through the new rule.

So the rest of the day went to the root cause. Claude wrote the PRs; I reviewed and merged them between 10:49 AM and 11:55 AM, and they deployed at 3:49 PM.

| Change | PR | Measured effect |
|---|---|---|
| WAF rule codified in Pulumi, so a later `pulumi up` doesn't delete it | #392 | — |
| Spot pool widened from 2 to 10 instance types; rolling config updates one instance at a time | #392 | Spot placement score 3 → 9 |
| Search heading escaped with `format_html` arguments; same sink fixed in the page context and the admin | #393 | reflected XSS closed; `?query={0}` no longer returns 500 |
| Default list no longer grows on every render in `get_hidden_inputs` | #394 | — |
| Remaining admin `format_html` helpers escaped | #395 | — |
| Facets sidebar rendered once instead of once per result year | #396 | each copy had re-run every facet count |
| Stored, GIN-indexed `search_vector`; one evaluation per page; 200-character query cap; facet counts on ids; per-search query logging removed | #397 | `/policies/?query=asylum` SQL time 1,528 → 262 ms; home page 2,514 → 101 ms (local) |
| Policy row data prefetched on list pages | #398 | `/policies/` 721 → 220 queries; `/biden/` 9,950 → 222 |

The last two rows are the real fix. A six-fold cut in search SQL time and a 45-fold cut in queries on one page means the same flood would now cost the database a fraction of what it did, and ordinary crawler traffic, which had RDS spiking to 33-92% before the attack, should stop doing that.

## Caveats

- The 25 minutes is from when I started looking, not from when the outage started. Alerting that reaches a person is on the follow-up list.
- Recovery took about 15 minutes after the block, not seconds. The likeliest reason is work already queued on the instances from clients that had given up, but that is an inference. Long-running queries are less likely, since the database went idle within a minute when the instances were terminated at 8:11 AM.
- Claude ran the commands, but I approved every change to production state, and the signature was validated against a week of logs before the block. I wouldn't skip either step to save time.
- The exact header value isn't published here. It's the site's own origin, which anyone can work out, but there's no reason to make the next fingerprint easier.

## Summary

- A residential-proxy botnet (at least 210,000 IPs, 8 rotating user agents, about 1.3 million requests) flooded an uncached, unindexed search page and pegged the database at 99%. Every instance went out of service because the health check queued behind the database.
- From first command to block was 25 minutes, with Claude running the investigation and me reading, steering, and approving.
- The block was one exact-match WAF rule on a hand-built Referer value that appeared 12-33 times a day normally and 2,000-3,500 times a minute during the attack. Errors hit zero nine minutes after it went live. It costs about $1 a month.
- The wrong turns (my Spot hypothesis; Claude's region, misread column, and timezones; a log source neither of us used) each cost minutes and each became a rule for next time. The timezone one left a wrong number in a commit message.
- Seven PRs merged within about an hour cut search SQL time from 1,528 to 262 ms and queries on one page from 9,950 to 222, closed a reflected XSS, and codified the WAF rule so it survives the next infrastructure deploy.

One person with an agent and CLI access went from an emergency message to a verified block in 25 minutes, and to root-cause fixes in production the same day. The part that needed a human was knowing which of the agent's numbers to believe and which of my own instincts to drop.
